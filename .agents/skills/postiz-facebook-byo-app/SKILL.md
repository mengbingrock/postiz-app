# Postiz Facebook BYO App

Set up a Meta app owned by the Postiz operator, then connect a Facebook Page using that app's credentials. Keep the app unpublished during initial testing unless the user needs accounts outside the app's roles.

## Establish the deployment values

Determine the public HTTPS origin of the Postiz instance before changing Meta settings.

```text
POSTIZ_ORIGIN=https://post.truegrit.dev
CALLBACK_URL=${POSTIZ_ORIGIN}/integrations/social/facebook
```

The callback must use the exact scheme, hostname, path, and trailing-slash form generated by the deployed Postiz instance. Do not substitute `localhost` for a public deployment.

## Create the Meta app

When the user requests browser execution, use their signed-in Meta developer tab. Creating an app is an external mutation, so do it only when the request authorizes creation. Let the user complete password, two-factor, CAPTCHA, or other security challenges; never read or enter those credentials.

1. Open [Meta for Developers](https://developers.facebook.com/apps/).
2. Create an app with a clear deployment-specific name.
3. Select the **Manage everything on your Page** use case under **Content management**.
4. Connect the operator's business portfolio when available. This is recommended for later verification and publication.
5. Confirm creation and record the generated App ID. Do not expose the App Secret in chat, logs, command output, screenshots, or source control.

## Configure the app

### Basic settings

In **App settings -> Basic**:

- Set **App Domains** to the hostname only, for example `post.truegrit.dev`.
- Confirm a monitored contact email.
- Add real privacy-policy and user-data-deletion URLs before publishing the app.
- Save, reload the page, and verify the domain persisted. Meta may report a successful save while omitting a value whose supporting fields are incomplete.

### Facebook Login for Business

In **Facebook Login for Business -> Settings**:

- Enable **Client OAuth Login**.
- Enable **Web OAuth Login**.
- Keep **Enforce HTTPS** enabled for a public deployment.
- Keep strict redirect matching enabled.
- Add `CALLBACK_URL` under **Valid OAuth Redirect URIs**.
- Save changes, then use Meta's **Redirect URI Validator**. Continue only when Meta reports that the URI is valid.

### Page permissions

In **Use cases -> Manage Pages -> Permissions and features**, ensure these permissions show **Ready for testing**:

- `pages_show_list`
- `business_management`
- `pages_manage_posts`
- `pages_read_engagement`

These are the minimum permissions for listing managed Pages and publishing through Postiz. Add these only when the requested features need them, because they normally require additional Meta review:

- `pages_manage_engagement` for comment management
- `read_insights` for analytics

Do not request optional scopes during the initial publishing connection.

## Connect the app in Postiz

1. Open **Add Channel -> Facebook Page**.
2. Enter the Meta **App ID** and **App Secret** in the Postiz UI.
3. Continue to Facebook and approve the four required scopes.
4. Select the Page managed by the authenticated Facebook account.
5. Confirm the channel appears in Postiz and can create a test post.

The App Secret should travel only from the Meta dashboard to the authenticated Postiz backend. Do not ask the user to paste it into chat.

While the Meta app is unpublished, only accounts assigned an app role can authorize it, and the authorizing account must manage the target Page. For other users, complete Meta App Review, business verification, required policy URLs, and app publication.

## Postiz implementation invariants

When implementing or reviewing BYO-App support in Postiz:

- Generate the OAuth URL on the backend; the browser submits credentials to an authenticated POST endpoint.
- Include the App ID as `client_id`, but never put the App Secret in the authorization URL.
- Encrypt the App ID/secret while stored in pending OAuth state and in the connected integration's persistent custom-instance details.
- Delete pending credentials after the callback consumes them.
- Exchange authorization codes and long-lived tokens through form-encoded POST bodies so the App Secret does not appear in URLs.
- Reuse the connected channel's encrypted credentials for reconnect operations.
- Return sanitized integration responses that omit access tokens, refresh tokens, App Secrets, and encrypted credential blobs.
- Keep the Graph API version configurable. For this deployment, the tested default is `v26.0`.

The expected callback is:

```text
GET /integrations/social/facebook?code=...&state=...
```

The expected setup endpoint is:

```text
POST /integrations/social/facebook/custom-oauth
```

## Verify and troubleshoot

Before declaring success, verify:

- Meta's redirect validator accepts the exact callback.
- The authorization URL contains the expected `client_id`, exact `redirect_uri`, and only the four required scopes.
- The authorization callback completes without exposing credentials.
- Postiz lists the Facebook Page and persists the new channel.
- A small test post publishes to the selected Page.

Use these failure mappings:

- **Missing required parameter: client_id**: Postiz did not receive an App ID, the deployment is serving an old frontend/backend pair, or the legacy OAuth route bypassed the BYO setup endpoint.
- **Invalid App ID**: the App ID is mistyped, belongs to a deleted app, or the wrong Meta product/app is being used.
- **redirect_uri_mismatch**: compare the requested URI with Meta character-for-character, including HTTPS, hostname, path, port, and trailing slash.
- **Permission or feature unavailable**: add the permission to the Manage Pages use case; for non-role users, request Advanced Access through App Review.
- **No Pages returned**: confirm the Facebook account has full Page access and an app role while the app remains unpublished.
- **Generic Meta error after login**: check app mode, business association, contact email, required policy fields, OAuth settings, and the Meta app's alert/required-actions pages.

Do not publish the Meta app, submit App Review, make a test post, or connect an additional account unless the user's request authorizes that external action.
